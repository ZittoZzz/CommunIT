## Public boundary, membership and provenance

Full profile membership is reconciled separately from source health. `source_membership` snapshots are keyed by resolved profile path. App startup and CLI reconcile the full configuration; CLI does so **before** `--source` selection. Exclusion removes membership, never the historical source row, event or revision. Different profiles retain separate membership; health still describes the latest stored route observation, not an independent per-profile check. Use `source_states(db, profile=resolved_path, active_only=True)` for active coverage; unfiltered calls are historical diagnostics. Direct programmatic partial `collect()` calls do not retire membership.

`announcement_discovery` records source/path/query separately from the current announcement. Two routes to one numeric Meetup ID produce one listing with both paths retained internally. Multiple roots within one adapter reuse the page fetch and retain both paths. Already-lost historical paths are not invented; saved run reports remain evidence. Directory disappearance is not an API-confirmed deletion and does not cancel or withdraw an event. Conflicting/recurring dates remain unverified.

Public `/api/events` uses an explicit visitor projection: no source inventory, search query, traversal path, index IDs, budgets, retry/cooldown messages or manual capability/token fields. `/api/sources` returns 404. The frontend has no inventory panel, “Our sources” link, discovery trace, source-health empty-state text or collection controls. It keeps event announcement/registration links, publisher attribution, field evidence, linked-only warnings, eligibility, distinct deadlines and review notes. Generic route names are not passed off as publisher identity; the announcement hostname is the fallback. Organizer URLs can remain legitimate evidence citations.

“Listings last updated” now means the latest **retained verified event-page check among saved listings**. Its tooltip states that not every listing was checked then. The API supplies `listings_updated_at` from verification evidence, not route success, search observation or page-load time. Partial runs can advance it if a page was actually verified; successful searches with zero verified pages cannot. Unknown legacy proof displays “Not recorded yet.” This is a deliberately narrower claim than content collection, not last code deployment.

Diagnostics remain in local SQLite and CLI reports. The old explicitly enabled, localhost/token-guarded collection endpoint remains internal for existing local tooling; no public frontend code or event response advertises it. It is disabled by default. No admin dashboard/authentication system was added. See RUN_LOCAL.md for CLI collection and reports.
