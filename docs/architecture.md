# Implementation notes

`backend/source_index.py` loads the publisher index into the existing source configuration. `backend/collect.py` orchestrates independently committed source jobs. `backend/adapters.py` discovers new posts through public APIs, feeds, and publisher indices and rechecks retained announcements. `backend/luma.py` reads public city/publisher calendars and discovered event pages. `backend/relationships.py` extracts explicit publisher relationships, and `backend/publishers.py` stores candidates and links qualified recurring monitors. `backend/network.py` enforces bounded reads and robots policies. `backend/extract.py` extracts explicit CTF identities and labeled fields without an LLM. `backend/domain.py` defines date precision and lifecycle. `backend/db.py` stores events, announcements, revisions, source health, and run reports in SQLite WAL mode. `backend/metrics.py` evaluates historical registration evidence. Flask serves read-only JSON and the Vite build. No public mutation endpoint, form, background browser scraper, or client credential is used. The classification follow-up adds distinct past-date and undated-search-lead displays to the existing UI.

## Backend publisher index

`sources.json` references `source-index.json` through `publisher_index`. Each publisher has a stable ID, name, role (`organizer`, `resharer`, or `both`), coverage, enabled flag, qualification status, and reason. An entry either references a legacy source using `source_id` or supplies one recurring `monitor` configuration. Duplicate publisher/source IDs, unknown references, and unsupported adapters fail configuration validation before collection. Existing unreferenced sources remain operational. Both Flask and the collector use this loader; the index is backend configuration, not a second public event directory.

The index contains 17 publisher/calendar records, with twelve enabled monitors: ROOTCON, UP Manila, Hack The Box Meetup Manila, AWS student communities in Mindanao, CREST, Luma Manila, KakaComputer's CTF RSS feed, Cyber404's partnership RSS feed, CyberPH's Luma calendar, Cisco NetConnect's Luma calendar, MLH Global Hack Week, and Safe AI Philippines. FEU Tech Eventually, University of Mindanao Student Developers Community, OWASP Cebu, the Philippine Information Agency, and VEKTR remain disabled candidates. The [source-index report](source-index.md) preserves the original ten-record checkpoint and lists later additions. [Publisher and registration-opportunity verification](publisher-opportunity-report.md) covers the latest iteration; [Luma discovery](luma-discovery.md) and its [verification JSON](luma-verification.json) retain the prior results. No historical event URL or supplied acceptance-case identifier is a runtime seed. One-time publisher setup is allowed; future competition links must come from that recurring source.

Disabled monitors remain in source health with `status: disabled` and their reason; the collector makes no request and preserves prior success history. Direct monitors run before supplemental search. Tavily uses only free keyless requests, while Brave remains disabled in the default zero-API-fee configuration regardless of local credentials. The index does not automatically activate an unknown publisher found through search.

The UI groups these rows after its unchanged filter/sort under **International online opportunities**. Fetch failures retain explicit route outcomes and cannot become successful zero-match checks. Exact saved-response replay uses the same ingest path and preserves first-seen and uniqueness.

## Discovered publisher candidates

Candidates discovered during collection are stored separately from configured monitors. `publisher_candidates` holds identity, first/last-seen timestamps, and any qualified monitor association. `publisher_identity_keys` records exact URL or namespaced account aliases. `publisher_relationships` retains the named role, announcement URL, source, optional event ID, discovery path, quote, and observation times. These additive tables participate in each source's ingestion transaction; a failed source cannot leave partly created candidate relationships. Repeated identical evidence updates last-seen without duplicating the candidate or relationship, while changed quotes remain separate evidence observations.

An accepted event can identify a host, organizer, co-organizer, sponsor, or partner. Publisher-news sources may retain explicit partnership leads without an event ID; they do not create a competition from that relationship alone. HTML extraction is restricted to relevant article paragraphs and role clauses. Navigation, footer, share-button, and unrelated links cannot establish a relationship. Winner recaps retain historical competition evidence and closed registration instead of advertising entry.

Candidate identity prefers a stable public publisher URL or a namespaced account ID. Known Luma profile aliases and supported Facebook profile/group shapes normalize conservatively. Individual Facebook post URLs are evidence, never inferred publisher profiles. Conflicting existing account aliases require review. Display-name similarity never merges two organizations. Without a public identity, a name is scoped to its evidence URL: a repeated mention in that announcement is stable, but the same name in another article remains unmerged. No website or social account is guessed for an unlinked sponsor.

Candidates remain inactive until a recurring source is qualified. One-time setup adds a normal source-index monitor, sets its active status, and supplies `publisher_identity_urls` or `publisher_account_ids` in the monitor configuration when its recurring URL differs from the candidate's public identity. After the configured source has a successful health check, `sync_configured_publishers` associates the existing candidate with the index ID, source ID, recurring URL, and verification time. It does not create discoveries for every configured publisher, mutate the index, or enable unverified Facebook profiles. A later fetch failure preserves the prior verification; disabling the configured monitor leaves the candidate inactive. Runtime reports expose candidate identities, roles, event associations, and supporting relationships for review.

## Identity and updates

An event key uses organizer, series, edition, region, and stage. ROOTCON and TCON edition numbers are identities; HackForGov uses its explicit year/edition and regional/stage context. Other named CTFs require an explicit year and normalize announcement/registration/teaser wording from titles. An opted-in publisher can identify a CTF from the article body when it explicitly describes a competition; a title year or labeled event date establishes the edition. A publication timestamp or unrelated copyright year does not establish that body-identified edition. Generic references, writeups, undated evergreen descriptions, and unidentified editions are withheld. A repeated canonical URL for the same event updates its announcement rather than creating another event. A reused URL with a different edition remains a different event. Tracking parameters are stripped; Facebook’s meaningful post IDs are preserved.

This is conservative deterministic matching, not unrestricted entity resolution: unrelated titles without a shared recognized identity can be missed or need a new series parsing rule. Unknown regions/stages are not assumed equal to known ones. The configuration is for organizers/feeds and reusable extraction rules, not manual event entry. Tests prove teaser → registration enrichment and distinct qualifier/regional-final/national-final, year, and region identities.

Exact shared non-Facebook article URLs can keep organizer corrections on one existing event. Distinct publisher announcements can share one event when they cite the same specific registration URL, both retain evidence for that link, and organizer identities agree or one was unconfirmed. Both cases require the same normalized series, edition, region, and stage; multiple competing matches are withheld. Generic form endpoints, homepages, and fuzzy title similarity are insufficient. Existing event IDs and first-seen timestamps are preserved, and distinct article links remain separate supporting announcements.

URL normalization is publisher-specific. Live CREST archive/article evidence established a trailing-slash convention for its `/event/` paths, so its direct monitor and matching search relationship use that same narrow rule. It does not strip or add trailing slashes globally, identify arbitrary host aliases, or equate opaque Facebook permalinks with numeric post IDs.

Current facts are recomputed from each announcement’s latest observation in publication order. A detected edit uses observation time to allow an old page to carry a correction. Repeating an unchanged fetch does not change its first-seen timestamp or revision count. Revisions retain extracted facts, field evidence, source ID, and observation time, not page snapshots. Additive schema migrations preserve older rows; missing historical evidence and source IDs remain unknown instead of being reconstructed from current facts. Older announcements discovered late cannot overwrite newer dated updates. Postponements clear the active schedule and deadline while preserving prior announcement evidence; explicit rescheduling supplies replacements. Missing announcements after a failed fetch remain available. Social API-confirmed deletions remove cached facts/history and hide events with no remaining evidence.

## Dates and status

Each competition start, end, tournament day (`competition_date`), registration opening, and deadline is a separate `{raw, value, precision, timezone}` value. ISO timestamps with an explicit offset and named-month times explicitly labeled PHT/Asia/Manila/UTC can be converted. Date-only values remain dates. Missing years, ambiguous numeric dates, and ambiguous timezones (including `PST`) remain verbatim text. No year, cutoff time, local timezone, midnight start, or duration is guessed. Publication time never becomes competition time.

Wrapped article labels such as `Event Details: / Date: / October 8, 2031` can establish a tournament day when the body explicitly identifies a competition and the context is not a conference or training program. Explicit `Tournament date` labels are also supported. A `Happening on` date can establish the day of a meetup's CTF when the same sentence directly says the dated event will feature the competition. This does not borrow workshop dates or whole-program clock times for the CTF. New date-only schedules replace stale bounds, new start/end bounds replace stale tournament days, and postponements clear both while retaining their historical evidence. Existing records whose date was never extracted require reprocessing of source evidence; the listing does not parse dates out of summaries.

Confirmed timestamps display in Asia/Manila. A confirmed end instant or explicit organizer completion notice moves an event to `finished`. A date-only end with an explicitly known zone can do so after that calendar date has passed in Manila. All calendar-day placement comparisons use Asia/Manila: today's date stays eligible until the next Manila day begins. This comparison does not change stored precision or timezone and does not manufacture a midnight timestamp. A past announced calendar day without confirmed completion instead produces `status: past_date, section: past`. The UI groups `past` and `finished` under **Past & finished**, preserving the **completion unconfirmed** distinction. A same-day passed timed start with no end remains **End unconfirmed**; a confirmed future end keeps a multi-day competition live.

Conflicting supported date claims retain their dates, roles and quotations in `date_conflicts`, clear the selected schedule, and appear under **Date unconfirmed**, outside Upcoming and Past. Start/end roles permit an ordered multi-day range; a date and a timestamp on the same Manila day corroborate each other. A dateless update does not resolve a conflict; a later supported dated correction can. Conflicts are not resolved by choosing whichever claim is future-dated.

Registration is evaluated separately. An expired confirmed deadline closes registration but does not finish a competition. A historical open invitation with a past competition date becomes registration **unknown**, not an invented closure. Cancelled and postponed competitions retain explicit labels in Upcoming & live; neither is falsely called completed. Genuine teasers retain **Schedule TBA**. An all-search-only event without a confirmed schedule receives **Undated search lead**, with an explicit notice that timing and current entry are unknown.

## Registration observations

Collection reports include `registration_observations`, one assessment per retained event, and `verified_timely_count`. This measures evidence already observed by the collector; it is not the independently selected benchmark's score. The benchmark stays frozen in research documentation and is never imported by runtime code.

A confirmed tournament day already past at observation prevents a stale open assertion from qualifying as timely registration. A publisher's advance-notice interval is measured separately from retained collector `first_seen` and registration observations. Publication dates never backdate discovery. Legacy run-start first-seen stamps must be labeled with their precision rather than represented as exact response receipt times.

Each revision is evaluated at its stored `observed_at`, using that revision's `facts_json`, `evidence_json`, and source ID. A verified observation requires explicit open registration, evidence for the open assertion and deadline, and a confirmed deadline instant later than the observation. A supplied registration-opening time must also be confirmed, evidenced, and already reached. Date-only deadlines, ambiguous times/zones, missing proof, and historic invitations first fetched after their deadline remain `not_verified` with explicit reasons. The helper does not borrow current proof to validate an older observation or backdate discovery to the publisher's posting time.

A completion, cancellation, postponement, or closure already observed for the event blocks a stale open invitation. A later closure does not erase an earlier qualifying observation. The report returns the earliest verified timestamp and its announcement/revision/source IDs, registration window, and supporting quotes. This supports future daily measurement without claiming that a backfilled invitation was a useful alert.

`evaluate_live_open_observation` adds a separate observation for competitions without a published deadline. It requires `registration_state: open`, retained evidence marked `basis: live_registration_widget` by the adapter, and an evidenced competition start or end instant later than the observation. Known passed deadlines/ends and lifecycle/registration blockers still reject it. Static announcement wording cannot provide the live-control marker; a stale open widget on a past event is insufficient. Approval-required and waitlisted entry remain distinct from open registration.

Each event summary retains its earliest `live_open_observation`, supporting revision/source/URL and evidence, plus `first_seen_while_live_open`. Reports aggregate these as `live_open_observation_count` and `first_seen_live_open_count`. They do not modify `verified_timely_count`, infer a missing cutoff, or change the frozen benchmark. Publication time is never substituted for first-seen time.

`event_context.py` also supports a narrow recap-to-calendar identity join when headlines differ. A recap must explicitly identify the complete program subject and kickoff date in its lead paragraphs; the calendar must independently supply that exact subject and local calendar date. Edition, stage and geographic conflicts veto the join, and multiple matching events are ambiguous. Context and both evidence URLs are retained separately from competition dates. A kickoff slot never becomes an invented complete competition interval.

## Job operation

Run collection with `python -m backend.collect`. CLI source selection, database path, and report path are configurable. The default database lives under ignored `data/`; `--report` can write a report elsewhere. A filesystem lock prevents scheduled/manual jobs overlapping. Each source is isolated: one failure does not roll back another source’s successful update. A partial source reports warnings and retains its prior complete-success timestamp. A job exits successfully if at least one source works and nonzero if no source succeeds; inspect the source panel/report for partial coverage. An `ok` check with zero accepted announcements proves readability, not competition discovery. Disabled candidates, blocked access, rate-limited checks, and other fetch failures are reported separately.

HTTP 429 `Retry-After` values are parsed as seconds or an HTTP date. The HTTP client enforces a host cooldown within the run, and source health persists `next_retry_at` so a new invocation cannot immediately repeat that source's request. Other monitors continue. Luma stops trying alternate routes or event details during a provider cooldown. A failed request or a city-feed item aging out never deletes an earlier listing. Source success and first-seen/registration observations retain their actual check times; a failed retry does not advance the previous complete-success timestamp.

The Linux user timer runs at 06:00 Asia/Manila with missed-run catchup. It shares the CLI, backend environment, database, and lock with on-demand runs, and reloads the index on each invocation. The install script also runs the local Flask website under a user service. Logs go to the user journal. Keep `.env` private and out of version control. To use another scheduler, invoke `.venv/bin/python -m backend.collect` once daily from this directory with the same environment. The [README](../README.md) provides exact commands to run the default job twice on one fresh temporary database without touching the production database or timer.

## Adding sources

A source requires a stable `id`, descriptive `name`, `kind`, recurring `url`, and supported scope rules. Public social accounts additionally set `actor`, organizer identity, lookback, and page budget. HTML sources specify allowed publisher hosts and a discovery link pattern; the collector traverses those index links automatically. An `index_only` archive can list additional recurring `index_urls`, such as a past-events calendar. Only permitted links discovered from those indices become article requests. RSS/Atom sources inspect feed bodies and retained articles; a complete-content feed can supply updated text directly. Only explicit CTF announcements are accepted. Verify recurring-source access and retain qualification evidence before enabling an integration; fictional parser fixtures cover its supported structure. A verified advance invitation establishes a CTF-invitation source. An exploratory publisher calendar such as Cisco's remains explicitly unproven for that purpose, even though its recurring access works. No credentials are read by React.

RSS `follow_articles: true` follows newly discovered entry links on configured hosts, including entries with generic teaser titles. Publisher-specific article/title/exclusion selectors remove sidebars and related-news blocks. A unique CTF heading with its own explicit year may identify an event inside a generic article; multiple competing headings are withheld. `body_identity` additionally supports a descriptive invitation title when the body establishes a competition and its edition. UP Manila's generic `capture the flag` WordPress feed query demonstrates that path. An explicit standalone CTF component heading on the configured AWS student event page identifies that component without treating the whole conference schedule as CTF times.

RSS monitors can opt into `discover_publishers` to retain explicit relationship evidence from feed/article bodies. `publisher_news` additionally retains relevant source-only leads when no competition qualifies. `relationship_scope` accepts supported Philippine host/organizer relationships rather than assuming that a Philippine sponsor, audience, or publishing website makes every event local. KakaComputer uses the existing RSS adapter for historical CTF corroboration and publisher leads. Cyber404 uses that adapter for partnership leads; partnership news alone is not an event.

Publisher metadata is retained separately from organizer facts. For `resharer` and `both` publishers, organizer attribution needs a supported body statement or configured verified organizer relationship; otherwise the organizer remains unconfirmed. A local publisher alone does not establish Philippine scope: the article must supply a local venue or separately verified organizer relationship. Reshares are not labeled as official organizer announcements. PUP's legacy feeds retain their explicit hosting/organization guard. Feed excerpts never replace a retained article when its refresh fails.

Announcements retain publisher metadata, `discovery_path`, `related_links`, and `field_evidence`. Direct Facebook post links and `plugins/post.php` embed targets inside the article body are stored as `linked_only`; the collector does not request them or copy their details. They do not create a second announcement or event. Ordinary profile/footer links do not establish discovery of an event post. Linked PDF attachments are also retained as links without claiming their unread contents. The UI shows the publisher article and discovered post link separately. Current field evidence follows the fact selected during reconciliation, and postponement clears evidence for the cleared dates. JSON run reports include accepted URLs, paths, event IDs, related links, and adapter rejection decisions. Facebook `story.php`/`permalink.php` search results are recognized when their owner matches an explicitly configured account alias; that support neither grants post access nor expands the search to unknown organizers.

Explicit labeled same-month competition date ranges expand into date-precision endpoints. Missing-year ranges remain raw text; no posting year or clock time is borrowed. Dates visible only in unread linked media remain unconfirmed.

CTFtime is a supplement: it queries bounded monthly windows and accepts on-site Philippine locations or configured Philippine organizer names/IDs. Mere mention of Filipino participation in a global event’s description is insufficient. CTFtime-only evidence is labeled as a CTFtime listing, not falsely labeled an official organizer post.

This was one-time research-assisted qualification, not automatic search discovery in the daily run. Both feeds include online events. CyberPH supplied historical CTF evidence; Cisco's calendar access is verified but CTF discovery remains unproven. WorkFlow PH is not enabled without a qualifying recurring route and CTF invitation evidence.

Configured publisher aliases identify only the verified Luma account. A same-name Facebook candidate remains separate without independent identity evidence. Neither calendar membership, a Philippine-looking name, nor an account timezone establishes Philippine scope for a future online CTF; each accepted event needs supported scope evidence.

Calendar entries supply discovery links only. The adapter follows those links and reads the public event description, hosts, location, schedule, and registration metadata. It requires actual cybersecurity competition evidence even when the title omits CTF, plus a confirmed Philippine venue or Philippine organizer. Membership in the Manila city calendar alone does not prove scope. The initial calendar check found ordinary events and no qualifying CTF; it established a working monitor, not a timely registration discovery. ## Free search discovery

`backend/tavily.py` issues the generic queries in `sources.json` through Tavily's documented keyless Search API. `Client.post_json` uses an anonymous session, sends no API key/cookies, rejects redirects, and bounds request time and response size. There is no paid fallback. A short `Retry-After` allows one retry; a longer or exhausted quota skips remaining queries to the same provider. Other source jobs continue. A failed query is distinct from a successful zero-result response; only a completely successful source run advances `last_success`.

Each query audit retains its parameters, status, attempt history, and all returned URLs/titles before filtering. Filter decisions are reported separately. Complete snippets, raw content, generated answers, and media are not retained. Search snippets may contain related posts and are never passed into event extraction. The standalone `python -m backend.tavily_check` diagnostic uses these same queries and transport without opening a database. Optional comparison arguments only inspect returned results and are not sent to Tavily.

Search titles must identify a CTF edition and establish Philippine scope: explicit local wording, the known Philippine HackForGov program, or a verified organizer/series relationship. A configured account is a publisher, not automatically the organizer of everything it shares. It supplies organizer attribution only when the title names it as host/organizer or matches its configured `event_pattern`. A university reporting foreign participation does not qualify. Unknown organizers stay unconfirmed. This deliberately conservative title-only policy can miss legitimate events; rejected URLs remain available in the audit.

Verified relationships can also specify `publisher_hosts` for partner websites that publish the organizer's announcements. These match exact ordinary-web hostnames, including explicitly configured `www` forms, and retain the same organizer/series ownership guard. A partner's unrelated competitions and lookalike domains remain excluded. This adds reusable partner discovery without seeding individual event links.

New search records are `search_only` and `official: false`, with no inferred schedule, registration, eligibility, publication time, or format. Their primary link is labeled “Search result · verify source.” Full-source records take precedence; search rediscovery cannot overwrite full facts or advance the full record's observation time. Query provenance remains visible in announcement history. Numeric Facebook IDs deduplicate equivalent URLs before event creation, while conflicting explicit years, known regions, qualifiers, and regional/national finals remain separate even if a publisher reuses a post. Opaque permalink tokens are not assumed equivalent to numeric IDs. Cross-post identity still requires matching event identity or the strictly guarded shared links described above; an opaque Facebook token does not establish equivalence to another URL form.

## Optional community discovery pilot

`opportunity_search` reuses the normal collector and announcement storage. It accepts generic queries through the existing keyless search transport, or a complete, separately captured public-search manifest via `search_results_path`. The latter records its actual provider and is an experiment input, not an autonomous search service or an event seed list. Every returned URL/title is audited. A fair per-query traversal verifies supported public event platforms and follows actual calendar links one level deep. The shared page budget includes ownership checks; unsupported URLs, unreadable pages, rate limits, and deferred pages remain explicit decisions. Search snippets never become event facts.

`opportunity_pages` verifies primary Luma, Meetup, and GDG pages and delegates Devpost overviews to `devpost`. Luma community parsing is shared with configured organizer calendars; price, ticket restrictions, signup availability, and event dates remain independent fields. The shared Devpost verifier reads the captured organizer overview and distinguishes typed submission cutoffs from registration cutoffs; conflicting primary dates remain unverified. Existing Philippine CTF gates remain unchanged. The opt-in CTFtime setting `include_international_online` follows directory-discovered organizer URLs and requires matching primary edition and schedule evidence before accepting an international online CTF. A directory schedule alone cannot establish price or current signup.

A temporary configuration may set `listing_window_days: 45`. The normal `/api/events` path then places undated, out-of-window, and recurring signup-unverified records in Watchlist. It uses event start, registration cutoff, or submission cutoff, never event end as a substitute cutoff. Already-stored date-only events remain eligible throughout their Manila calendar day without gaining an invented start time. The default legacy listing remains unchanged when this setting is absent. The frontend renders Watchlist with the existing filters. Public approval applications share the same action priority as ordinary open registration, while their approval requirement remains visible. Within current actions, explicitly verified free entries precede unknown-price or paid entries; the existing date order breaks remaining ties.

Prototype runs must supply an explicit new `--database` and temporary configuration; preview the resulting database with matching `CTF_SOURCES`. Captured search results and responses, database snapshots, and evaluator references are not runtime configuration committed to this repository. The Nov 22 reference is a known regression set after disclosure; it cannot establish a new blind score.

## Student topic filters

The student directory uses the IT_Community_PH brand. `backend/topics.py` projects `topics` and `topic_evidence` from active saved announcements in the normal `db.events` listing path. The seven topic keys are `cybersecurity`, `ai_data`, `cloud_devops`, `software_development`, `networking_systems`, `community`, and `general_it`. An event can have several independently supported topics. This read-time projection covers existing and new records without rewriting stored facts, changing the legacy `topic` field, or rerunning collection.

Topic labels require retained subject evidence from verified organizer announcements; an explicitly evidenced CTF competition can also be corroborated by a fetched partner notice. Search-only titles, organizer/sponsor names, audience-only metadata, and unsupported legacy topic values do not establish subjects. Organizer-backed descriptions, agendas, and learning objectives can establish subjects; program text retained in legacy eligibility fields is recovered for the same shared projection. Community requires an organizer-described purpose of meeting peers, sharing projects, or building a tech community; titles, organizer identities, routine networking breaks, and recruitment alone are insufficient. Networking & Systems covers technical networking and administration. General IT requires explicit broad/general technology scope. When the saved excerpt is insufficient, the event has no topic tags and remains visible under All topics. Evidence citations retain their original source sentences.

The frontend applies one selected topic alongside text search, Format, and Registration before the existing sort and geography grouping. Returning to All topics changes only that filter; Clear filters resets all filters. Section counts reflect the active filters, while the header overview describes the whole directory. Official event titles and the existing ranking remain unchanged.


## Compact event browsing

The student listing is a single column of collapsed event rows. The leading date is the start day in Asia/Manila (or the retained date-only event day), without inventing a time; uncertain/conflicting dates display Date unconfirmed. Title, organizer, location/format, supported topics, and known joining facts remain visible. Register by and Submit by are separate fields; an unknown cutoff has no preview row. Paid and waitlisted are independent facts, and ongoing events retain their submission action.

Native Details controls expand in place with keyboard support. Details contains full Manila times, description, eligibility, pricing, registration, official links, and source history, with unknown facts explicit. Program text recovered from legacy eligibility appears under Description; Who can join is reserved for audience or entry requirements. The Region filter is removed, while location, PH/international-online grouping, the other filters, and ranking are preserved. This is a read-time projection over stored evidence; no database migration or collector rerun is required.
