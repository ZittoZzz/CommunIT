# IT_Community_PH repository guidance

## Start here

- Read [PROJECT_CONTEXT.md](PROJECT_CONTEXT.md) before making changes. It records the latest verified state, completed work, limitations, and evidence paths.
- Use [RUN_LOCAL.md](RUN_LOCAL.md) for preview setup, startup, shutdown and checks from the repository root. Fresh clones need an explicitly supplied populated saved snapshot; routine setup must not use the main database, live collection or installed services.
- Inspect the current code, `git status`, and relevant configuration. This checkout contains substantial uncommitted work; preserve changes unrelated to the user's task.
- Use `sources.community.json` for broad community collection tests; it excludes the legacy individual AWS seed and applies profile-local qualification decisions. Follow the source-admission rules in `docs/source-index.md`. Reconcile full profile membership before partial collection; never delete historical sources/events for exclusion. Deployment defaults remain separate. Keep benchmark scoring inputs outside runtime discovery.
- Treat the handoff as a dated checkpoint. Verify current files, database selection, and running processes before acting; do not assume recorded counts or process IDs are still current.

## Scope and data boundaries

- Public navbar brand: **CommunIT** (exact accessible home-link name), using the approved cork-board/two-note SVG, dark Commun and green IT with a short brown underline. Browser title: **Tech Board | CommunIT**, with the matching corkboard SVG favicon. No visible hero title/subtitle or student-only eyebrow; retain a visually hidden **Tech events** H1. Search starts directly below the navbar. Show **Philippines · PHT** beside Events, accessible as **Philippines, Philippine Time**, including on mobile; date rendering still uses Asia/Manila. Keep repository/package names and URLs unchanged.
- Reuse the existing collector, storage, normal API, and student listing paths. Preserve existing CTF behavior. The approved frontend uses the Campus Bulletin cork finish, compact date-first cards, and one pinned detail paper.
- Use an explicit preview/test database for development. Protect `data/ctfinder.sqlite3` (the main/production database); do not modify it, deployment services, or schedules without user authorization for that action.
- Starting the backend can initialize schema and register source metadata. Set `CTF_DATABASE` explicitly before starting it, even for UI checks.
- Do not run discovery merely to test display changes. When collection is requested, use the authorized public-source workflow and an isolated database. No paid APIs or logged-in Facebook scraping.
- Preserve frozen benchmark artifacts and original scores. Known-reference regression checks are not blind evaluations. Never seed runtime discovery with benchmark titles, individual event URLs, expected answers, or replay fixtures.
- Keep useful local databases and verification output under ignored `data/` paths. `/tmp` is suitable for disposable tests, not the only copy of a useful snapshot. Do not commit databases, credentials, or captured private data.

## Event behavior

- Sort listings by the Manila calendar date displayed on each card, earliest first within each geography group; unknown/conflicting dates go last. Signup status and price do not affect order. Preserve stable order for same-day ties and keep deadlines distinct from event dates.
- Preserve date-only precision. Use Asia/Manila calendar days; do not invent start times or deadlines. Keep conflicting dates unresolved.
- Keep the preview's 45-day listing window and separate PH opportunities from international online opportunities. Unverified recurring signups and undated leads keep their backend Watchlist classification and appear publicly under Needs confirmation.
- Classify topics from supported event evidence. An organizer name alone does not prove Cloud, and “hackathon” alone does not prove Software Development. Events without supported topics stay visible under All interests.
- HackForGov/Hack4Gov series identity may establish Cybersecurity from a retained matching title citation, including a search-only lead. This does **not** verify its schedule, price, eligibility, organizer identity, or signup.
- A bare CTF agenda heading does not establish a separate competition or make an entire conference a cybersecurity event. Preserve official titles and distinguish conference tickets from competition entry.
- Public browse controls are Search events (“Event, organizer, or school”), Browse by interest (“All interests”), and How to attend (“Online, in person, or both”), in that order. Both dropdown defaults show all. Registration status never filters public listings, including legacy URL/storage values; confirmed signup badges remain. Show at most four represented interest chips below the controls, labelled **Interests in these listings** with the hint **Select to filter**, derived before the interest filter (current search/attendance/section); chips and dropdown share selection, with aria-pressed and toggle-off preserving search/attendance. Keep labels/chevrons visible, defaults muted/readable, search widest on desktop and its own row on mobile; wrap controls/chips without clipping.
- Section tabs attach directly above the cork board. Use compact equal-height paper tabs with clipped corners, a forest-green active edge, and a short reduced-motion-aware lift when selected. Order them Upcoming, Past, Needs confirmation, Archive. Hide the archive count when zero. Needs confirmation combines backend unconfirmed/watchlist records without changing their underlying status or notes. Do not restore All events or separate Watchlist/Date unconfirmed tabs. Keep the original wood-colored board frame and fixed card/paper accents. Important source/review notes appear near the top of the paper, before dates and signup facts; do not rely on color alone.
- Show listings freshness below the filters on arrival, in Manila time. Use `listings_updated_at`, backed by retained event-page verification, never route success, search-only observation, page load or a failed attempt; omit the entire freshness line when the timestamp is missing or invalid. This is the latest verified page among saved listings, not a claim that every event was refreshed.
- Use the section tabs for section labels/counts; do not repeat a heading stamp inside the board. Keep Refresh saved listings in Directory updates below the board. Collection and diagnostics use the local CLI/reports; no public route inventory, source-health panel, search/traversal traces or diagnostic switches. Clear filters stays beside the search/filter controls.
- Desktop card selection must preserve the list position; mobile Back to the board must restore filters, scroll, and selected-card focus. Prototype demo records and finish toggles do not belong in the live UI.
- Keep unknown price, deadlines, eligibility, and signup facts unknown. Distinguish blocked/unreadable sources from successful checks with zero matches.
- In cards and the pinned paper, omit absent/placeholder optional facts and empty sections rather than printing Unknown rows. Suppress generic eligibility fallbacks; preserve concrete eligibility, verified Free/zero prices, paid fees and boolean account requirements. Show supported registration status independently of known registration/submission cutoffs. Use a combined Manila schedule with original date/time precision, deduplicate attendance labels without losing venues or hybrid meaning, and keep one primary “View organizer’s page” action using the specific organizer event URL when recorded. Show a separate Register action only for a different destination. Keep search-only uncertainty in the prominent review/source notes; never expose the Sources & updates dropdown, evidence blocks, source-link lists or collector refresh history in the public notice. Preserve all underlying evidence records for maintainers. Do not infer new facts or rewrite event data for presentation.
- The pinned notice uses the same `EventDate` component as its selected card, including uncertainty and explicitly labelled parent-event dates. Give its month strip forest green and a single 210 ms press/settle on selection, including mobile reopening; respect reduced motion. Keep a thin green paper edge, responsive serif title and organizer directly beneath it. Immediately after important review notes, place the stamp beside the supported schedule and venue; keep street addresses secondary, cancellation/postponement/reschedule status adjacent, and parent-event schedules explicitly distinct from the CTF schedule. Render schedule/location once in this lead, never again in the fact grid. Preserve natural wrapping on narrow phones.
- Group remaining attendance/interests/eligibility/price/account/signup/deadline facts inside a **What we can get** section with dotted top/bottom rules; place the heading in the top rule near the right edge, with no explanatory note beneath it. Use a semantic two-column fact grid with uppercase labels and bold values; stack fields on narrow phones. Omit this section when no remaining facts exist. Attendance has its own field; strip duplicate format words from the paper location while preserving city/venue and hybrid details. Cards retain their compact location/format label. Interests uses existing supported topics, deduplicated and labeled as on the cards. Keep original-event/registration actions below the facts. The primary organizer link has a short uneven light-green underline, visible keyboard focus, and a small reduced-motion-aware hover lift/pressed state. Keep the search panel forest green with quiet decoration and readable controls/chips; prototype controls and dialogs stay out of production.
- Shared venue display may use current, fully fetched Schema.org Event.location evidence tied to that event’s own page: city on the compact card, venue/locality and useful street/floor details in the paper. Never use organizer addresses, unrelated event URLs, old announcement evidence, search-only records or malformed/truncated location JSON to guess a venue. Broad/online records retain their supported location/format. Keep confirmed cancellation/postponement and explicitly evidenced current reschedules beside the schedule; refresh/revision timestamps alone are not attendee updates.
- Review flags are public notes, not an admin system or a reason to hide a listing. Unresolved undated leads expire after 45 days from first discovery into Archived leads, accessible through the Archived leads tab; expiry never asserts completion. Search rediscovery must not renew verification or the expiry clock.
- Keep Cloud and DevOps separate and evidence-backed; a tool or organizer name alone does not establish either topic. Use the stable numeric Meetup event ID for revisions and duplicate display reconciliation. Preserve original rows/history, and retain conflicting source dates for review instead of choosing a convenient date.

## Verification and handoff maintenance

- Run checks appropriate to the change. For backend behavior, use isolated pytest fixtures; for frontend behavior, use browser checks and the frontend build. Do not launch a production service or collector as a substitute for tests.
- Before finishing a task that changes the system, **update PROJECT_CONTEXT.md** with the resulting behavior, affected paths, verification actually run, and remaining gaps. Use the Asia/Manila date and distinguish new verification from earlier results.
- Update this `AGENTS.md` when durable project rules change. Update `RUN_LOCAL.md` when startup, shutdown, database preparation, ports, or environment variables change. Keep the files consistent.
- Keep the handoff concise and current: revise superseded state, retain significant decisions, and link to detailed reports instead of copying chat transcripts. Do not rewrite frozen historical reports to match later results.
- For unfinished work, record the exact remaining task and blocker. Never claim a check passed if it was skipped, blocked, or only inferred.
- In the final response, state what changed, verification results, material limitations, and whether the handoff was updated.
