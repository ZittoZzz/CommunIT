# IT_Community_PH repository guidance

## Start here

- Read [PROJECT_CONTEXT.md](PROJECT_CONTEXT.md) before making changes. It records the latest verified state, completed work, limitations, and evidence paths.
- Use [RUN_LOCAL.md](RUN_LOCAL.md) for preview setup, startup, shutdown and checks from the repository root. Fresh clones need an explicitly supplied populated saved snapshot; routine setup must not use the main database, live collection or installed services.
- Inspect the current code, `git status`, and relevant configuration. This checkout contains substantial uncommitted work; preserve changes unrelated to the user's task.
- Use `sources.community.json` for broad community collection tests; it excludes the legacy individual AWS seed and applies profile-local qualification decisions. Follow the source-admission rules in `docs/source-index.md`. Reconcile full profile membership before partial collection; never delete historical sources/events for exclusion. Deployment defaults remain separate. Keep benchmark scoring inputs outside runtime discovery.
- Treat the handoff as a dated checkpoint. Verify current files, database selection, and running processes before acting; do not assume recorded counts or process IDs are still current.

## Scope and data boundaries

- Public navbar brand: **CommunIT** (exact accessible home-link name), using the approved cork-board/two-note SVG, dark Commun and green IT with a short brown underline. Browser title: **Tech Board | CommunIT**, with the matching corkboard SVG favicon. No visible hero title/subtitle or student-only eyebrow; retain a visually hidden **Tech events** H1. Search lives inside the navbar, taking its own navbar row on phones. Show **Philippines · PHT** beside Events, accessible as **Philippines, Philippine Time**, including on mobile; date rendering still uses Asia/Manila. Keep repository/package names and URLs unchanged.
- Reuse the existing collector, storage, normal API, and student listing paths. Preserve existing CTF behavior. The approved layout follows `CommunIT-board-pair.html` on the existing navbar/cork structure: a warm, irregular, low-contrast cork surface fills the page beneath the navbar, with centered working margins, compact cream date-first cards in a tan folder, and one pinned detail paper. The desktop list takes slightly more than half of the working area. Keep the structure in React and canonical CSS; do not copy prototype DOM-reparenting scripts or accumulate layout overrides. No sidebar search, hero, separate green search panel, wooden frame or viewport-edge rails.
- Use an explicit preview/test database for development. Protect `data/ctfinder.sqlite3` (the main/production database); do not modify it, deployment services, or schedules without user authorization for that action.
- Starting the backend can initialize schema and register source metadata. Set `CTF_DATABASE` explicitly before starting it, even for UI checks.
- Do not run discovery merely to test display changes. When collection is requested, use the authorized public-source workflow and an isolated database. No paid APIs or logged-in Facebook scraping.
- Preserve frozen benchmark artifacts and original scores. Known-reference regression checks are not blind evaluations. Never seed runtime discovery with benchmark titles, individual event URLs, expected answers, or replay fixtures.
- Keep useful local databases and verification output under ignored `data/` paths. `/tmp` is suitable for disposable tests, not the only copy of a useful snapshot. Do not commit databases, credentials, or captured private data.

## Event behavior

- Use forest-green keyboard focus throughout the board instead of blue, retaining clearly visible outlines and system Highlight in forced colors. Search and filter controls share ivory/sage hover and focus treatments, subtle reduced-motion-aware color transitions and pressed feedback. Theme native page scrollbars with rounded green thumbs and cream tracks where supported, matching the panel scrollbars. Preserve native wheel/touch physics and immediate scroll restoration; do not intercept wheel input or force smooth scrolling.

- Sort listings by the Manila calendar date displayed on each card, newest first in **Past**, earliest first in the other tabs, within each geography group; unknown/conflicting dates go last in either direction. Signup status and price do not affect order. Preserve stable order for same-day ties and keep deadlines distinct from event dates.
- After section/search/attendance/interest filtering, group cards by that same event day within each geography. Use a labelled section per day (for example **Wed, Nov 25**), with unresolved/conflicting dates in a final **Date to confirm** group and no empty groups. Reuse `eventDay`; registration/submission cutoffs never define a group. Keep the existing date stamps and stable same-day order. Day headings use opaque folder-colored backgrounds and CSS sticky positioning bounded by their own sections, so the next day pushes the previous heading away. Desktop listings scroll natively in their own keyboard-accessible region; phones retain page scrolling. Navbar and filters currently scroll normally, so sticky day headings use top zero; account for any future persistent toolbar.
- Preserve date-only precision. Use Asia/Manila calendar days; do not invent start times or deadlines. Keep conflicting dates unresolved.
- Keep the preview's 45-day listing window and separate PH opportunities from international online opportunities. A confirmed ongoing event (`live` from the existing lifecycle rules) stays eligible for Upcoming even after its start and without a future deadline; after its confirmed end it appears in Past on the next listing reload. Preserve uncertain/date-only bounds and the separate guard for unverified recurring signup. Unverified recurring signups and undated leads keep their backend Watchlist classification and appear publicly under Needs confirmation.
- Classify topics from supported event evidence. An organizer name alone does not prove Cloud, and “hackathon” alone does not prove Software Development. Events without supported topics stay visible under All interests.
- HackForGov/Hack4Gov series identity may establish Cybersecurity from a retained matching title citation, including a search-only lead. This does **not** verify its schedule, price, eligibility, organizer identity, or signup.
- A bare CTF agenda heading does not establish a separate competition or make an entire conference a cybersecurity event. Preserve official titles and distinguish conference tickets from competition entry.
- Public browse controls are navbar **Search events** (“Event, organizer, or school”), followed by compact, side-by-side **Browse by interest** and **How to attend** disclosure buttons. Their closed text is the original label when inactive and **Interest · choice** / **Attend · choice** when active, with the full choice accessible. Each opens a warm ivory chip panel with a tan border, green top edge and shadow; only one panel opens at a time. Preserve existing topic/attendance values, including Format unconfirmed. **All interests** / **All attendance options** are first and reset only their own group. Chips are single-select buttons with aria-pressed and a visible selected checkmark. Apply immediately, close and return focus to the trigger; support outside click/focus dismissal, Escape, Tab, arrow/Home/End navigation and Enter/Space selection. Keep aria-expanded, selected-choice announcements and keyboard focus visible. Panels overlay tabs/cards without layout shifts or clipping; use the available filter width on phones and wrap chip labels. Opening animation is 150ms and respects reduced motion. This supersedes native selects and always-visible chip suggestions; do not add a Free only row. Search, interest, attendance and section combine. Registration status and price never filter listings. Clear filters resets search/interest/attendance while preserving section. Keep the filter panel compact: 6px vertical padding, 36px desktop triggers (40px on phones), and no bottom margin on the freshness line. On listing cards, place location/attendance, supported topics and signup status together in one wrapping metadata row to save height; keep review, lifecycle, price and deadline facts below. Omit empty rows.
- Section tabs sit directly above the left-hand tan listing folder. Use compact, level, equal-height paper tabs (36px desktop, 40px mobile) with clipped corners, a forest-green active edge, preserved counts/keyboard navigation and a short reduced-motion-aware lift when selected. Order them **Upcoming**, **Past**, **Needs confirmation**, **Archive**; let long labels wrap at narrow widths and put counts beneath labels on 320px phones so all four remain available. Keep folder top/bottom padding at 6px and day-heading spacing compact to prioritize visible listings. Hide the archive count when zero. Needs confirmation combines backend unconfirmed/watchlist records without changing their underlying status or notes. Do not restore A–D letters, staggered dividers, All events or separate Watchlist/Date unconfirmed tabs. Selected cards retain their green left edge. Important source/review notes appear near the top of the paper, before dates and signup facts; do not rely on color alone.
- Show listings freshness below the filters on arrival, in Manila time. Use `listings_updated_at`, backed by retained event-page verification, never route success, search-only observation, page load or a failed attempt; omit the entire freshness line when the timestamp is missing or invalid. This is the latest verified page among saved listings, not a claim that every event was refreshed.
- Hydrate the last successful public board synchronously from versioned `sessionStorage` (`communit:board:v1`) before the first render, then refresh through the existing `/api/events` request. A validated empty response is a saved board; a visited flag, malformed cache or unfinished request is not. Without saved data, show the pinned opening/error ticket; with saved data, keep the board interactive and use the cream checking/success/error slip beneath the navbar. Keep the navbar-to-board gap compact (32px desktop, 42px on phones for wrapped errors); reserve the slip’s space without moving the board when status changes. Failures retain saved data and offer Retry; storage failures must not break live loading. Preserve current controls, selection and scroll on refresh, including changes made during the request. Cache only public board fields, never collection metadata/tokens; do not manufacture verification timestamps. Use polite status announcements, preserve focus, and respect reduced motion. No prototype replay controls or artificial initial-load delay.
- Use the section tabs for section labels/counts; do not repeat a heading stamp inside the board. Keep Refresh saved listings in Directory updates below the board. Collection and diagnostics use the local CLI/reports; no public route inventory, source-health panel, search/traversal traces or diagnostic switches. Clear filters stays beside the search/filter controls.
- Align the desktop pinned notice with the top of the filter area in a stationary, bounded two-column working area. Both the event list and notice use the same native scrolling, reserved gutter and scrollbar styling: hide thumb/track at idle, reveal on pointer/keyboard/touch/scroll activity, then hide after roughly one second. Contain desktop scroll overshoot so reaching either boundary does not scroll the page or nudge the notice; do not use sticky positioning on the notice. Paint the sheet around its gutter to prevent a blank strip. Keep visible keyboard focus and a native forced-colors fallback. Phones retain page scrolling. Desktop selection preserves list position; mobile **Back to the board** restores filters, selected card, scroll and focus.
- Keep the reference's small stick-figure notes decorative and noninteractive below the board. Reveal them after scrolling without reserving first-screen space or covering controls. Respect reduced motion for tabs, stamps, actions and decorative notes. Prototype demo records, comparison/finish controls and simulated organizer dialogs do not belong in the live UI.
- Keep unknown price, deadlines, eligibility, and signup facts unknown. Distinguish blocked/unreadable sources from successful checks with zero matches.
- In cards and the pinned paper, omit absent/placeholder optional facts and empty sections rather than printing Unknown rows. Suppress generic eligibility fallbacks; preserve concrete eligibility, verified Free/zero prices, paid fees and boolean account requirements. Show supported registration status independently of known registration/submission cutoffs. Use a combined Manila schedule with original date/time precision, deduplicate attendance labels without losing venues or hybrid meaning, and keep one primary “View organizer’s page” action using the specific organizer event URL when recorded. Show a separate Register action only for a different destination. Keep search-only uncertainty in the prominent review/source notes; never expose the Sources & updates dropdown, raw evidence maps, source-link lists or collector refresh history. Preserve all underlying evidence records for maintainers. Do not infer new facts or rewrite event data for presentation.
- The pinned notice uses the same `EventDate` component as its selected card, including uncertainty and explicitly labelled parent-event dates. Give its month strip forest green and a single 210 ms press/settle on selection, including mobile reopening; respect reduced motion. Keep a thin green paper edge, responsive serif title and organizer directly beneath it. Immediately after important review notes, place the stamp beside the supported schedule and venue; keep street addresses secondary, cancellation/postponement/reschedule status adjacent, and parent-event schedules explicitly distinct from the CTF schedule. Render schedule/location once in this lead, never again in the fact grid. Preserve natural wrapping on narrow phones.
- Put remaining attendance/interests/eligibility/price/account/signup/deadline facts inside the warm-yellow **What we found** sticky note, using the semantic **Event facts** grid (its heading is visually hidden). Give the note a subtle static tilt and place the facts on a lighter cream inset with a muted left rule; do not animate the note on scroll. Do not put event descriptions, source excerpts or no-excerpt fallback text inside this note; the existing Description section stays separate below the organizer actions. Preserve original rows/history, and retain conflicting source dates for review instead of choosing a convenient date.

## Verification and handoff maintenance

- Do not push routine follow-up changes unless the user explicitly asks; the user handles publishing.

- Run checks appropriate to the change. For backend behavior, use isolated pytest fixtures; for frontend behavior, use browser checks and the frontend build. Do not launch a production service or collector as a substitute for tests.
- Before finishing a task that changes the system, **update PROJECT_CONTEXT.md** with the resulting behavior, affected paths, verification actually run, and remaining gaps. Use the Asia/Manila date and distinguish new verification from earlier results.
- Update this `AGENTS.md` when durable project rules change. Update `RUN_LOCAL.md` when startup, shutdown, database preparation, ports, or environment variables change. Keep the files consistent.
- Keep the handoff concise and current: revise superseded state, retain significant decisions, and link to detailed reports instead of copying chat transcripts. Do not rewrite frozen historical reports to match later results.
- For unfinished work, record the exact remaining task and blocker. Never claim a check passed if it was skipped, blocked, or only inferred.
- In the final response, state what changed, verification results, material limitations, and whether the handoff was updated.
